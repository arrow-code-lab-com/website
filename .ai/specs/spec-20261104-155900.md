# 仕様書（draft）: トップページの問題点を Issue に分けて順に改善する

> status: draft
> 作成日: 2026-11-05 / 協議レベル: medium
> 次のステップ: /ai-run {Issue番号} 要望整理（または /ai-graph-runner {Issue番号} 要望整理）

## 1. 背景と課題

### 1-1 原文

> それぞれの問題点についてIssueを作り、ひとつづつ解決していきます

「それぞれの問題点」は、直前に行ったトップページ（`src/components/HomePage.astro` ほか）のレビューで挙げたものを指す。

### 1-2 読み取った内容

レビューの結論: 今の文面は「何をしている事業か」の説明止まりで、訪れた人が「自分の困りごとを頼めそうだ」と思える材料が足りない。大きな問題は次の 3 つ。

1. 誰の・どんな困りごとを解決するのかが書かれていない（文言が抽象的）
2. 実力を示す材料が少ない（スキル未記載、アプリは公開予定の 1 本だけで中身の良さも伝わっていない）
3. 問い合わせの前で不安が増える並びになっている（「お受けできない依頼」が問い合わせ直前、相談してよい内容の例がない）

レビューで挙げた問題点（Issue に分ける単位の候補）:

| 対象 | 問題点 |
|---|---|
| Hero | キャッチコピーが誰にでも当てはまる／リード文が自己紹介／CTA が 1 つでページ内スクロールのみ／文字だけで視覚要素がない |
| Services | 説明が一般的／自社アプリが受託サービスと並んで受託の印象を薄める／対象・規模感・成果物が書かれていない |
| Apps | カードがアイコンと 1 行のみで、詳細ページの材料が伝わらない／依頼者向けの「実績」としての見せ方になっていない |
| About | スキル未記載（TODO）／「一貫して対応」の裏づけがない／個人名を出さない分の信頼材料がない |
| Flow | 期間の目安・用意してほしいもの・相談/見積もりが無料か・契約の形が書かれていない |
| Notice | 断る条件が問い合わせ直前にある／副業の条件が合う依頼者に向けた書き方になっていない |
| Contact | 何を書けばよいかの案内、ハードルを下げる一言がない |
| サイト全体 | `og:image` がない／トップの `<title>` が屋号だけ／スマホのヘッダーにお問い合わせボタンが目立たない／アクセス解析がない（未決） |

レビューで出した改善のアイディア: 「こんなご相談に対応できます」の具体例、自社アプリを開発事例として見せる、About の信頼材料、副業を強みとして書き直す（「こんな方に向いています」）、問い合わせのハードルを下げる、FAQ の追加、見た目の強弱と og:image・title、セクション順の見直し。

### 1-3 未定の事実（ユーザーに確認が要る）

- 相談・見積もりを無料にするか
- 公開してよい経験年数・得意な技術の範囲
- NDA への対応、ソースコードの権利、納品後の修正対応の方針
- 公開してよい GitHub などのアカウントの有無
- RoomCheckPDF を「1 人で企画からストア公開まで」と書いてよいか

## 2. ゴール

問題点ごとに Issue を作り、1 件ずつ解決する。（Issue の分け方・順序・各 Issue の完了条件は要望整理で決める）

## 3. 要件

- CLAUDE.md の方針を守る（金額・個人名・住所・電話番号・勤務先が特定できる情報・架空の実績を載せない。副業の条件と矛盾する約束を書かない。英語ページには依頼を受け付ける内容を書かない）
